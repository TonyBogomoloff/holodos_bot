# Holodos Bot

Telegram: [@holodos_recept_bot](https://t.me/holodos_recept_bot).

Два режима: блюда из холодильника и план питания по личному профилю.
Рецепты с фотографиями, составом, шагами и ссылкой на проверенный источник.

## Сценарий

1. Отправить фото, альбомом или отдельными сообщениями — распознавание запустится автоматически.
   Каждое следующее фото дополнит общий список; ответ появится под фото.
   Можно начать сразу со списка текстом или голосом.
2. Поправить список обычной фразой: «Это кефир, убери молоко, добавь рис».
   Неуверенные продукты отмечены «нужно уточнить» и не используются при подборе до уточнения.
3. Нажать «Подобрать блюда». Соль, масло и специи не считаются имеющимися автоматически.
4. Выбрать блюдо под альбомом. Если совпадений меньше пяти, можно разрешить докупку 1–2 продуктов.

Команды: `/start`, `/plan`, `/profile`, `/products`, `/new`, `/help`, `/privacy`, `/delete`.
Пожелания («без мяса», «не люблю грибы», «до 30 минут») сохраняются вместе со списком.

## План питания

1. `/plan` или кнопка «План питания». Профиль задаётся текстом/голосом: 1–12 человек,
   1–6 приёмов пищи в день, бюджет на всех с валютой и периодом, регион покупок, вкусы и ограничения.
   Неизвестные поля бот уточняет. Перед сохранением показывает полный профиль.
2. Выбрать день, неделю или две недели. Сначала бот показывает меню по дням. Стрелки дней обновляют то же сообщение и кнопки.
   Фото холодильника необязательно. Профиль редактируется через `/profile`.
3. Нажать блюдо: открыть рецепт с фотографией и количествами для числа людей или выбрать замену.
   Проверенные альтернативы загружаются заранее вместе с меню. Меняется только выбранный приём пищи.
   «Уточнить предпочтения» принимает текст или голосовое для этого приёма пищи конкретного дня.
   Бот ищет новые проверенные варианты с учётом пожелания и ограничений профиля; меню меняется
   только после выбора замены. Кнопка «⬅️» отменяет ввод пожелания.
   Внизу экранов, кроме главного меню, стоят «⬅️» и «🏠».
4. Когда меню выбрано, нажать «Что докупить». Покупки учитывают только выбранные блюда,
   число людей и имеющиеся запасы. Замены проверяются на примерный бюджет.
   КБЖУ — примерные на одну исходную порцию; дневная сумма — на одного человека, без назначения
   персональной нормы калорий. Это бытовое планирование питания.

План строится только из найденных веб-поиском рецептов разрешённых сайтов: страницы, состав,
шаги, число порций и фотографии проверяются. Вторая проверка сверяет состав и шаги с ограничениями;
неполный план не выдаётся за готовый. Перевод и состав источника сохраняются без придуманных замен.
Пищевая ценность учитывает [NutritionInformation](https://schema.org/NutritionInformation), если она
есть и понятна её база; иначе модель приблизительно оценивает КБЖУ по составу и исходным порциям.

Количество покупок суммируется на весь срок и всех людей. Сопоставление названий делает модель,
масштабирование и вычитание запасов — код. Один запас расходуется только один раз. Совместимые
единицы (кг/г, л/мл) приводятся к общей базе; масса не угадывается из чашек, упаковок или фотографии.
Неизвестные количества помечаются для уточнения. После изменения холодильника старые недостающие
количества не показываются как актуальные: предложено обновить план.

Стоимость — оценка нужного количества ингредиентов в валюте и регионе профиля, без интеграции
с ценами магазинов. Размер упаковки может увеличить чек. Если даже экономный набор превышает
пропорциональный бюджет на выбранный срок, бот предлагает уточнить бюджет/пожелания.

## Провайдеры и границы

- Python 3.12+, SQLite WAL, долговечная очередь с последовательной обработкой каждого пользователя.
- Groq `whisper-large-v3-turbo`; голосовые до 3 минут, аудиофайл до 8 MB.
- Только ChatGPT-authenticated Codex CLI, Luna `gpt-5.6-luna`, effort `low`.
  Отдельный платный OpenAI API и автоматическая смена модели не используются.
- Каждый поиск обязан содержать реальный вызов web search, ограниченный сайтами «Еда»
  (`eda.ru`, `eda.rambler.ru`), Budget Bytes и 1000.menu. Приложение отбрасывает ссылки на другие
  сайты и проверяет домен при каждом перенаправлении страницы; фото могут загружаться с публичных CDN.
  Затем приложение само загружает страницы, извлекает `schema.org/Recipe`, проверяет полный состав
  и фотографию именно из страницы рецепта. Поддерживаются JSON-LD и microdata основного рецепта
  1000.menu: состав с количеством, порции, время, фото и блоки шагов без рекламы и комментариев.
  Недоступные страницы, отсутствующие шаги/фото и неполные сопоставления отбрасываются.
  Поэтому пять результатов — цель, а не гарантия при любом наборе продуктов.
- Рецепты без структурированной разметки пока пропускаются. Не придумываются замены и рецепты.
  Количество неизвестных продуктов и свежесть по фото не гарантируются.
- Перевод сохраняет количество строк и числовые значения ингредиентов/шагов.
  Если проверка перевода не прошла после повторной попытки, бот отдаёт оригинал рецепта.
- Модель получает только данные конкретной задачи. Shell, файловые инструменты, plugins, apps,
  hooks, memories и делегирование отключены; конфиг Codex пользователя игнорируется.
  Web search включён только на этапе поиска. API-ключи не передаются в окружение Codex.
- HTTP-загрузчик блокирует локальные/служебные IP, проверяет редиректы и соединяется с проверенным IP
  без повторного DNS lookup; TLS проверяет исходное доменное имя.
- Важные результаты сохраняются перед отправкой. При неопределённом результате отправки Telegram
  альбом не дублируется автоматически: `/products` восстанавливает доступ к текущему списку.

## Конфигурация

`config.example.json` содержит только параметры. Пустой `allowed_user_ids` означает доступ всем
пользователям личных чатов; непустой список ограничивает доступ. Начальные лимиты: 30 операций
пользователя в сутки, 300 суммарно, 2 параллельных пользователя. Это локальные ограничения бота,
не гарантия доступности общих квот Groq/ChatGPT для соседних приложений.

Секреты читаются отдельно: `/home/tony/Desktop/_code/config.json`, поля
`bot_token_holodos_recept` и `groq_voice`. Значения не копируются в репозиторий.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python -m pip install --no-deps -e .
cp config.example.json config.json
.venv/bin/python -m holodos_bot check --config config.json --secrets /точный/путь/config.json
.venv/bin/python -m holodos_bot run --config config.json --secrets /точный/путь/config.json
```

`check` проверяет Telegram identity, отсутствие webhook и вход ChatGPT; не отправляет сообщения
и не доказывает работу LLM. Существующий webhook не удаляется автоматически.

## Проверки

```bash
.venv/bin/ruff check src scripts tests
.venv/bin/pytest -q
```

При изменениях запускать только относящиеся к ним тесты. Первоначальный выпуск проверяется целиком.
`scripts/smoke.py --config config.json --stage vision|asr|sources|search|all` явно запускает реальные провайдеры.
Этап `planning` проверяет реальный разбор синтетического профиля, недельный план с веб-поиском,
страницами/фото, ограничения, замену одного блюда, пересчёт покупок, навигацию по дням и открытие рецепта. Отправка Telegram
имитируется; пользовательская БД не читается и не изменяется.
Этап `sources` проверяет по одной живой странице каждого из трёх сайтов и загрузку её фото без вызова LLM.
Он использует синтетические изображения/речь и публичные рецепты, не читает переписку
и не отправляет сообщения. Для ASR fixture нужен ffmpeg с фильтром `flite`; для работы нужен `ffprobe`.

## Данные

Временные загрузки удаляются после завершения обработки. Список и правки живут до 24 часов
бездействия; завершённые задания и расшифровки — до 24 часов после получения. Очистка каждые 10 минут.
Профиль питания и последний план с покупками хранятся отдельно до удаления пользователем.
`/new` очищает только холодильник. Изменение профиля сбрасывает старый план.
`/delete` удаляет список, историю правок, профиль, план и задания пользователя;
суточный счётчик квоты сохраняется.
Резервные копии БД живут до 24 часов. Удаление здесь не удаляет историю Telegram или данные
из систем внешних провайдеров. Секреты, DB, временные файлы и логи исключены из Git.

## Деплой

Хост `my-server`, пользователь `tony`, приложение `/home/tony/Desktop/_code/holodos_bot`,
служба `systemctl --user status holodos-bot.service`.

- Код: `.releases/<SHA>`; `current` указывает на активный выпуск.
- Конфигурация и `data/` лежат отдельно и не перезаписываются релизом.
- `scripts/release.py build --output ... --base <production-SHA>` собирает только чистый коммит.
  Для первой установки `--base` не указывается. Коммит сначала должен быть отправлен в GitHub.
- Распаковать архив в `.releases/<SHA>`, выполнить `release.py prepare --candidate <path>`.
  Для целевых тестов передать `--tests tests/test_planning.py tests/test_bot.py`.
  Проверяются хеши, зависимости, выбранные тесты и авторизация; создаётся `validation.json`.
- `release.py install --candidate <path>` под deploy lock повторно проверяет production SHA,
  останавливает только этот бот с завершением текущей обработки, сохраняет БД, переключает код,
  запускает службу и проверяет меню, БД, состояние и хеши. При сбое возвращает предыдущий код.
  Данные автоматически назад не откатываются. Менять схему нужно совместимыми миграциями.
- `release.py status` показывает SHA, совпадение файлов и состояние службы.
  Нужна также реальная проверка изменённой функции. Сам по себе `active` её не заменяет.

Первое подключение SSH и авторизация Git/Codex уже проверены отдельно; ключи не хранятся в проекте.
